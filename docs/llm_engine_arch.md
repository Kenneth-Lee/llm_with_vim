# llm_engine的软件结构说明

llm_engine主要就提供一个函数：answer()，没有参数，它从标准输入获得内容，然后打
印输出到标准输出上。

这个过程分成两部分：

* \_parse\_input()，这部分读取用户的输入，读取的时候会实时返回输入回去（过滤临
  时注释），主要用于获得配置（组合Configure）和对话（找到每个角色的表达）。

* 组合输入，提交给LLM，实时输出LLM的输出

\_parse\_input()是个状态机管理的问题，就是根据每行的内容切换当前角色，然后把对
应的内容收集到对应的角色数据上。

组合输入则是个合并输入的内容，在Configure角色的配置上补充系统配合和默认配置等，
自动组合出一个最合适的参数。然后根据这个参数把对话消息发给LLM，然后实时把LLM的
输出按llm自己定义的格式，输出到标准输出上。

## \_parse\_input()状态机实现

\_parse\_input()的核心问题是：“当前的角色是谁”，这决定了我们在上下文中把什么信
息放到什么角色的定义中。它一行行处理，跳过注释，递归头文件，然后把剩余的信息收
集到当前角色上，一直到遇到角色切换的行，再提交到上下文中。

## 工具调用逻辑

工具调用在引擎中看作一种临时交互（这一点和很多Agent是不同的），LLM决定发起工具
调用后，调用引擎直接调用用具并把结果返回给LLM，这种调用和产生的上下文直接放在临
时注释中，最终LLM一Assistant角色回应的回答，才会被认为是回答。

所以，如果用户希望这些中间的运行结果作为影响LLM后续判断的上下文，需要手工控制这
些上下文。

## 关于功能插件化的思考

最近dsh的“一切皆插件”的设计理念流行，我们这里探讨一下把这种设计引入本工程的可能
性。

“一切皆插件”的需求在我们这里是存在的。我们把需求逻辑变成代码，本质就是需求的逻
辑是固定的，比如我们的Engine：我们先从一个固定的格式上解释用户要发给LLM服务器的
上下文，组装成请求，把请求发给服务器，然后解释服务器的返回，翻译成符合用户要看见
的格式，呈现在编辑器上。如果这些行为都是固定的，那不需要插件，一个程序就可以了。

但我们可能有不同的用户输入请求，比如用户有时用`@//`表示一种注释，有时希望用
`Configure`用用户语法表示配置，用`@@inc`包含其他文件……这些每个都是独立的功能，
而且还有可能扩展更多的的可能性。编码给不同的LLM webapi，也是根据不同的目标引擎
有不同的代码，如果用插件，直接调用不同的插件接口就行了，不用在一个程序中走不同
的分支，增加程序的复杂性。

所以，如果基于一个“一切皆插件”的平台来设计，完美的状态是：我们的主程序就是一个
插件，它实现一个工作流：读入编辑器的请求，调用用户输入解码器-组合器-LLM编码器
-LLM解码器-编辑器输出器，然后我们再在用户输入解码器中调用扩展语法器，处理不同的
“角色”发言，把这些发言送入组合器进行组合。

但除了做这样的事情，我们似乎并不会再写一个不一样的工作流。为此付出的代价是：我
们本来可以直接调用某个模块的，现在变成要“申请”某种名字的接口，然后把那个调用变
成一个“通用形式的服务请求”。这个成本看来不值得。

所以，更合理的后续架构发展方向是：我们还是按上面这个架构来组装我们的主程序，在
可以多选的位置上，我们引入插件，插件表现为某个目录中的一个py文件，其中声明自己
的服务名称，每种名称支持不同的调用函数，主程序按某种策略进行单选或者多选，调用
对应的函数，也不做dsh式的自动资源释放，如果有资源申请和释放的需要，封装在不同的
固定调用中就可以了。
