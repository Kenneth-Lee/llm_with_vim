# @@inc原语的设计思路

@@inc原语的主要目的允许.llm文件可以包含其他文件作为公共的头文件（我建议用.llh定
义这种文件），我们把这种文件称为“LLM头文件”，或者简称“头文件”。以免每个文件都要
写相同的内容。所以我们有三个基本期望：

1. 在主文件中写成@@inc了，提交以后这个地方还是@@inc，不会被展开。

2. @@inc包含的文件被看作无条件插入到所在位置解释，所以如果@@inc文件中包含了其他原
   语，那么那些原语就好像定义在主文件中一样，不会做其他解释。

3. 如此类推，如果一个被@@inc包含的文件中再出现@@inc原语，那么它也是无条件认为被读
   入的文件是被插入到所在的位置。最终所有这些文件的行会形成一个顺序的序列

为了做到这一点，我们引入一个堆栈形式的数据结构，我们处理主文件的时候，如果遇到
@@inc原语，那么主文件的内容和它处理到的行，这些作为状态，可以压栈，然后我们开始
处理被@@inc的文件，这个@@inc文件被处理完以后，我们从堆栈取出之前的状态，继续处理
前一个文件，直到堆栈中最后一个文件全部被处理完。

为了避免循环依赖导致无限循环，我们引入一个堆栈上限，堆栈深度超过10（这个可以设
置为一个配置参数）以后，我们生成一个表达错误的调试信息，然后跳过这个@@inc原语。

所以，总结起来说，llm_engine的功能是一行行处理输出，如果某行包含了@@inc，那么这
行替换为对应头文件的多行，继续一行行处理。这样，就算处理的是包含了@@inc的行，也
好像处理一个单一的.llm文件一样。

## 关于config角色的处理逻辑

除了@@inc和注释行，剩下的内容都被归类为不同角色的“发言”，提交给LLM服务器。其中
System，User和Assistant角色定义的都是真实提交的消息，只有Config是用于定义参数的
角色，它只定义如何提交请求。所以Config只能定义一次。如果Config这个虚拟角色“发言”
多次，后一个定义就覆盖前一个定义，所以无论你定义多少次，最终提交请求用的都是最
后一个Config角色的定义。如果到最后一行也没有Config角色的定义，那么llm_engine会
在最后补上默认的定义，以便用户可以看到这个定义，或者以这个定义为模板，调整具体
的定义。
